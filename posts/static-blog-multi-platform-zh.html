静态博客部署实战：一份构建，六个免费平台同步上线

2026-11-19

静态博客部署真正麻烦的地方，不是写页面，而是让同一份内容稳定地出现在多个托管平台上，并且每个平台的 canonical、sitemap、RSS 都指向它自己的域名。这篇文章记录我把自己这套博客同时推到六个平台的做法，包括踩过的坑和最后的取舍。

为什么值得做多平台部署

单一域名的风险很实在：某天平台改政策、免费额度收紧、或者账号被误判，整站就没了。把构建产物分发到多个静态托管后，任意一家出问题都只是少一个入口，内容和链接仍然在。

另一个收益是抓取覆盖面。不同托管商的 CDN 节点、域名权重、抓取频率都不一样，同一篇内容放在 GitHub Pages 和 Cloudflare Pages 上，被搜索引擎发现的速度经常差好几天。

代价是什么

内容必须只维护一份，发布必须全自动，否则多一处就多一份维护成本。这也是我坚持用命令行而不是后台点击的原因：只有脚本能保证每次发布路径一致。

静态博客部署的六个平台分工

下面是我现在在用的组合，按上手难度从低到高排列。

| 平台 | 发布方式 | 免费额度 | 适合场景 | |---|---|---|---| | GitHub Pages | git push 后自动构建 | 仓库公开即可 | 源站、其他平台的构建来源 | | Cloudflare Pages | wrangler pages deploy | 每月构建次数足够个人博客 | 主站、访问速度快 | | Netlify | REST API 上传 zip | 每月 100GB 流量 | 备份站、表单等附加功能 | | Render | 连 Git 仓库自动部署 | 免费实例会休眠 | 备用站、演示环境 | | InfinityFree | 面板上传 zip 解压 | 免费虚拟主机 | 传统主机形态的兜底 | | Firebase Hosting | firebase deploy | Spark 套餐 10GB 存储 | 海外访问、和 GCP 打通 |

这张表本身就是选型依据：能用命令行或 API 的优先，只能面板操作的最后上。

各平台的文档要先读

平台差异大多写在文档里。Firebase 的多站点配置见其托管文档，Cloudflare Pages 的构建环境说明也在官方文档中，Netlify 的部署 API 有完整的 zip 上传示例。先读一遍能省掉大量试错。

一份构建脚本要解决的三件事

第一，产物要能独立运行。样式、脚本、图片全部相对路径或者可访问的绝对 URL，不能依赖任何平台的默认行为。

第二，站点级元数据要按目标域名生成。sitemap.xml、rss.xml、canonical、og:url 里的域名必须和目标平台一致，否则搜索引擎会当成重复内容，多平台反而变成负资产。

第三，构建要可重复。同一篇文章构建多次，产物必须完全一致，方便对比和回滚。

我的构建命令大概是这个样子：

node src/scripts/build-blog.js \
  --out var/_global/blog-fb \
  --base https://bingblog-fb.web.app \
  --title "Bing Blog" \
  --limit 20

--base 是唯一需要按平台变化的东西，其余参数保持一致，这样六次构建的差异只在于域名。

元数据最容易出错的地方

常见错误是只改了首页域名，忘了 sitemap 和 RSS。解决办法是把 base 作为构建参数传下去，让所有模板都从同一个变量取域名，而不是每处硬编码。

发布流水线怎么串起来

我的入口是一条命令，按顺序做四件事：构建、推 GitHub、部署 Cloudflare 和 Netlify、部署 Firebase。任何一步失败都不影响其他平台，脚本会继续跑完并汇总结果。

GitHub 仓库在这里承担两个角色：既是 GitHub Pages 的源站，也是其他平台构建产物的分发点。Render 直接连这个仓库，push 之后就自动重新部署，不需要额外命令。

InfinityFree 这类只提供面板的主机是唯一的例外，需要用浏览器自动化把 zip 传上去再解压。

内容质量比部署更重要

多平台分发会放大内容问题。一篇水文发到一个站只是浪费一次机会，发到六个站就是把低质内容铺满搜索结果，反而拉低整站权重。

所以我现在给发布流程加了一道前置检查：字数、段落数、小标题数、代码块、图片数量按平台分别卡线，再跑一次内容质量评分，不达标就不允许发。评分维度包括标题、结构、内容密度、搜索意图匹配、可信度和软文程度，其中篇幅不足目标一半会直接否决。

各平台的字数门槛

参考国内三个内容平台的实际要求：掘金建议 1500 字以上，CSDN 建议 1200 字以上并带配图，知乎建议 900 字以上但更看重开头几段的信息密度。海外平台相对宽松，Dev.to 和 Hashnode 八百字左右即可。

常见问题

多平台发布会被判重复内容吗

会，如果 canonical 处理不当。每个平台都必须声明自己的 canonical，让搜索引擎把其他域名上的同一篇内容视为副本。

免费额度够用吗

个人博客的量级基本够。真正会超的是构建次数和带宽，前者靠减少无谓的重新构建，后者靠图片压缩和 CDN 缓存。

需要自建服务器吗

不需要。静态站的全部计算都在构建阶段完成，托管商只负责发文件，这是它比动态站省心的根本原因。

小结

静态博客部署的核心是把构建和发布彻底解耦：内容只写一遍，产物按平台重新生成元数据，发布交给命令。做到这三点，多一个平台只是多一行命令的事。
