把静态博客同时发布到五个免费平台：一份构建，五处上线

2026-11-19

为什么要多处部署

同一篇内容，放在不同域名下，能被不同的爬虫与推荐系统抓取；对个人博客来说，这比死守一个域名更划算。 关键是把「构建」和「发布」拆开：内容只写一遍，产物可以分发到任意多个静态托管。

五条通道与各自的做法

| 通道 | 发布方式 | 备注 | |---|---|---| | GitHub Pages | 构建产物推到仓库，Pages 自动发布 | 需要公开仓库 | | Cloudflare Pages | wrangler pages deploy <dir> | 一条命令，秒级 | | Netlify | REST API 建站 + zip 部署 | 需要 Personal Access Token | | Render | 直接连 GitHub 仓库，Publish Directory 填 . | push 后自动重新部署 | | InfinityFree | 面板上传 zip 并解压 | 传统虚拟主机，只能走面板 |

一份构建脚本的关键点

  1. frontmatter 解析：标题、日期、标签、站点，尽量保持简单；不要为了排版引入重型依赖。
  2. 绝对链接要按站点生成：sitemap 与 RSS 里的域名必须跟目标站点一致，否则搜索引擎会当成重复内容。
  3. 产物要能独立运行：样式内联或用相对路径，避免依赖某个平台的默认行为。
node src/scripts/build-blog.js --out dist --base https://example.com --title "My Blog" --limit 20

发布流水线

  • GitHub 仓库当作唯一事实来源；其它平台要么从它拉，要么由本地脚本推。
  • Cloudflare、Netlify 用 CLI/API 直接推产物，失败可重试。
  • Render 走 Git 集成，push 即部署，省一条命令。
  • InfinityFree 这类面板型主机，用浏览器自动化把 zip 塞进上传框并调用面板自带的解压接口。

小结

多平台发布真正的成本不在部署，而在「内容格式统一」和「链接一致性」。把这两件事收紧，剩下的都是几条命令的事。

static-sitedeploynetlifycloudflarerender
